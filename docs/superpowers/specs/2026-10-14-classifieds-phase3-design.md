# Phase 3 — Вторичный рынок (идеальное состояние)

Дата: 2026-10-14  
Продукт: Sogd Realty / Maskani  
Статус: согласовано в дизайн-сессии, ждёт ревью перед планом реализации

## Цель

Гражданин Согда может бесплатно подать объявление с телефона (как Авито/Циан), увидеть его на витрине и в карточке `/classifieds/[slug]`, управлять им в `/profile/ads`. Витрина читает PostgreSQL, не моки. Риелторы не пользуются этой формой — их канал CRM/Open API.

Работа двумя заходами:

1. **Живой рынок** — форма, фото, карточка, каталог, кабинет, автоодобрение.
2. **Доверие** — живая модерация вместо автоодобрения, антиспам, верификация телефона.

## Вне скоупа обоих заходов

- Интерактивная карта и lat/lng в UI (Phase 9).
- Нативное приложение (Phase 10).
- Смена ролей, SMS-провайдер как обязательная продакшен-интеграция в заходе 1.
- Реклама / промо-тарифы сверх уже существующего `isPromoted` в схеме.

## Роли

| Роль | Подача формы | Витрина / карточка | Мои объявления | Модерация (заход 2) |
|---|---|---|---|---|
| `user` | да | да | свои | нет |
| `realtor` | нет, экран «для граждан» | да | нет | нет |
| `developer` | нет | да | нет | нет |
| `admin` | нет | да | нет | очередь |
| гость | нет, модалка входа | да | нет | нет |

Кнопка шапки «Подать объявление»: нет сессии → `AuthModal` на вход, затем редирект на `/classifieds/new`. Сессия с ролью не `user` → страница-заглушка со ссылкой в CRM / кабинет застройщика.

## Маршруты (заход 1)

Публичные:

- `/` — блок вторички из `classifieds` со `status = active`.
- `/classifieds` — каталог с фильтрами: город, тип объекта, тип сделки, комнаты, цена.
- `/classifieds/[slug]` — карточка: галерея, цена TJS/USD, параметры, коммуникации, описание, «Показать телефон» / WhatsApp (как на главной: лид в `/api/crm/leads`).

Кабинет гражданина:

- `/classifieds/new` — мастер из 5 шагов.
- `/classifieds/[slug]/edit` — тот же мастер, только владелец.
- `/profile/ads` — список своих объявлений: фото, статус, просмотры, изменить, снять с публикации.

Навигация шапки: «Вторичка» ведёт на `/classifieds`, не на якорь `#classifieds`.

## Мастер подачи

Одна колонка, прогресс сверху, существующие Shadcn + изумруд Maskani.

1. Тип: `dealType` + `propertyType`.
2. Адрес: `city` (enum Согда), район, адрес, ориентир.
3. Параметры: зависят от типа (квартира — комнаты/этаж/площадь; дом — сотки; участок — сотки без комнат; коммерция — площадь). Коммуникации чекбоксами из схемы.
4. Цена и контакты: валюта ввода, вторая считается курсом `DEFAULT_USD_TO_TJS`; торг; имя, телефон, WhatsApp.
5. Фото: с устройства, drag-and-drop, сетка, первое — обложка, до 10 файлов, JPEG/PNG/WebP, ≤ 10 МБ каждое, клиентское сжатие перед upload. Минимум 1 фото.

Предпросмотр на шаге 5, затем публикация.

Валидация: Zod на клиенте по шагам и повторно на сервере. Без `any`.

## Статусы

Схема уже содержит `pending | active | rejected | archived | sold`.

Заход 1: `POST` создаёт строку и в том же запросе ставит `active` (автоодобрение; промежуточный `pending` в БД не обязателен). В `/profile/ads` сразу «Активно». Витрина показывает только `active`. Поле статуса и UI «На проверке» остаются в модели, чтобы заход 2 включил их без переделки экранов.

Снять с публикации: `archived`. Продан/сдан: `sold` (кнопка в кабинете). Редактирование владельцем не меняет статус `active` в заходе 1.

Заход 2 заменяет автоодобрение: запись остаётся `pending`, пока `admin` не одобрит (`active`) или не отклонит (`rejected` + причина в `notes` не вводим — причина в новом поле `moderationNote text`, nullable, добавляется миграцией в заходе 2).

## Данные и API

Таблица `classifieds` без новых сущностей в заходе 1. Главная и каталог не используют `CATALOG_PROPERTIES` как источник витрины. CRM-подборки (`/profile/crm`) в заходе 1 тоже читают active classifieds через API, чтобы подборки не расходились с рынком. Демо-seed остаётся стартовым набором.

`GET /api/classifieds`

- Без `mine`: только `active`, query: `city`, `propertyType`, `dealType`, `rooms`, `priceMin`, `priceMax`, `q`.
- `mine=1`: сессия обязательна, все статусы текущего `userId`.

`POST /api/classifieds`

- Сессия + `role === user`.
- Zod → insert `pending` → update `active` → `{ success, classified }`.
- Фото уже загружены, в теле только URL.

`PATCH /api/classifieds/[id]` — владелец, поля карточки.

`POST /api/classifieds/[id]/status` — владелец: `archived` | `sold`; в заходе 2 админ: `active` | `rejected`.

`POST /api/classifieds/photos` — сессия + роль `user`, upload в Storage, ответ `{ urls: string[] }`.

Ошибки: 401 без сессии, 403 чужая роль или чужой id, 400 Zod, 404 чужая/несуществующая карточка (не 403 на чужой slug в публичном GET — публичный GET отдаёт 404 если не `active` и зритель не владелец).

Просмотр: публичный GET карточки увеличивает `viewsCount` (один раз за загрузку страницы, без антибота в заходе 1).

## Фото (Supabase Storage)

Bucket `classified-photos`, публичное чтение, запись только authenticated в префикс `{userId}/`. Пути: `{userId}/{classifiedDraftId}/{n}.webp`.

Порядок: клиент получает draft id (`crypto.randomUUID()`), грузит файлы, затем `POST` объявления с массивом URL. Если `POST` объявления падает — экран «Повторить», URL уже есть, повторный POST без повторной загрузки. Если Storage падает — объявление не создаём.

RLS: политики bucket в декларативной схеме Supabase / SQL-миграции. Без публичной записи.

## UI-состояния

- Пустая витрина: короткий текст + «Подать объявление».
- Пустые «Мои объявления»: CTA в мастер.
- Нет фото / неверный тип / >10 МБ: ошибка на шаге 5 до upload.
- Мастер для не-гражданина: не форма, а объяснение.

Карточка объекта — единственное место с «карточной» подачей объекта. Каталог — лента превью (фото, цена, комнаты, район), не сетка дашборд-виджетов.

## Тесты захода 1

Unit/API (tsx + node:test, как store подборок):

- Zod: отказ без title/address/area/price/phone/photos.
- `POST` от `realtor` → 403.
- `POST` от `user` → запись `active` после автоодобрения.
- `GET` витрины не возвращает `archived` и `pending`.
- `POST .../status` archived → пропадает с витрины, остаётся в `mine=1`.
- Чужой `PATCH` → 403.

Браузерная проверка вручную после реализации: мастер → карточка → витрина → снять.

## Заход 2 — доверие

Включается только после рабочего захода 1.

- Убрать автоодобрение. Новые объявления остаются `pending`.
- `/developer-admin` не используем для гражданских объявлений. Новая страница `/admin/classifieds` только для `admin`: список pending, превью фото, одобрить / отклонить с `moderationNote`.
- Антиспам: не больше 3 `POST` объявлений с одного `userId` за 24 часа; скрытое honeypot-поле; отказ при >10 фото.
- Телефон: перед первой публикацией гражданин подтверждает `users.phone` одноразовым кодом. Провайдер за интерфейсом `sendPhoneOtp(phone)`; без ключа — демо-код в логах сервера (тот же приём, что Telegram без токена). Поле `users.phoneVerified` уже есть — выставлять true после успеха. Пока телефон не подтверждён, `POST /api/classifieds` → 403 с кодом `phone_unverified`.

## Критерии готовности Phase 3

Заход 1: гражданин публикует объявление с фото с устройства; оно на `/classifieds` и `/classifieds/[slug]`; правит и снимает в `/profile/ads`; риелтор формой не публикует; главная без `catalog-data` как источника вторички.

Заход 2: новое объявление не на витрине до одобрения админом; лимит 3/сутки; публикация только с `phoneVerified`.
